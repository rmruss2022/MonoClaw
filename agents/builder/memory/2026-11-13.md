
## openhome skip/duck polish (Nov 13)
- Skip was holding the NEW track at the listen-duck (6%) through the poll+announcement (~3.4s) → intro sounded cut off; and if `soloist ctl now` returned None, no announcement AND ducked intro (worst case).
- Fix: skip fast-path calls `duck(False)` right after `soloist ctl next` → new track at 100% immediately; polls for the name at full volume; announces only if found.
- `duck(on, level=None)` now takes a level. `speak()` uses `SPEAK_DUCK_LEVEL=35` (music stays audible under our voice) vs `DUCK_LEVEL=6` for listening (clean mic). `_soloist_now()` caps title[:45]/first-artist[:30].

## openhome audio-session model (Nov 13) — industry pattern
Researched Music Assistant / Home Assistant / Android AudioFocus: for an announcement you PAUSE/silence the music, play the voice with a VOLUME BOOST, then resume; for a track change the voice finishes BEFORE the music (re)starts.
Implemented in voice_client:
- Split `speak()` → `_say(text)` (low-level: TTS + `SPEAK_GAIN=1.4` boost via np.clip, plays to X10, no music mgmt) and `speak(text)` = pause music (soloist+sc pause) → _say → resume (soloist play). Voice never competes with music; music is silent under the voice.
- Skip: `next` → `soloist pause` (new track held silent) → poll name → `_say("Now playing X")` → `duck(False)` (vol 100) → `soloist play`. Song starts AFTER the announcement at full volume. Returns ("skip", None) so the loop doesn't double-speak.
- Listening still ducks to DUCK_LEVEL=6 (mic clean); SPEAK_DUCK_LEVEL now legacy/unused.
- Known edge: resume only does `soloist play` (Spotify); SoundCloud-source replies would leave SC paused — fix later if SC used.

## openhome: speech was quiet because X10 sink @ ~56% (Nov 13)
Diagnosis: TTS PCM is near full-scale and plays fine (isolated pw-play to X10 audible), but live announcements were lost — the X10 PipeWire sink sits ~0.56, so the voice played at ~56% and got missed before the full-volume song. Confirmed by playing the same clip at sink 1.0 (loud) vs 0.56 (quiet) — Matthew heard both, 2nd louder.
Fix: `_say()` now raises the X10 sink to `SPEAK_SINK_VOL=0.9` during TTS playback then restores prior level (`_get_sink_vol`/`_set_sink_vol` via wpctl @DEFAULT_AUDIO_SINK@). `SPEAK_GAIN` back to 1.0 (PCM already near full; 1.4 just clipped). Music level is set via soloist volume separately, so boosting the sink only makes the VOICE louder. Skip already forces soloist vol 0 + pause during the announcement.

## openhome voice AUDIBILITY — the big one (Nov 13, SOLVED)
Symptom: beep heard, but Jarvis's TTS replies NOT heard on the X10 (Bluetooth). Hours of dead ends (speaker volume, AVRCP drift, routing). Root causes found by RECORDING the X10 sink output (`pw-record -P '{ stream.capture.sink=true }' --target bluez_output...X10`):
1. **BT sink goes "idle" with no active stream** → the voice (played ~3-14s AFTER the beep, once the command is recorded) falls into an idle/sleeping sink and is dropped. Beep survives because it plays instantly while music still active.
2. **A DUCKED-but-active music stream (soloist vol 6) BLOCKS the voice from mixing out** to the BT sink — the voice pw-play returns rc=0 but the sink monitor shows rms ~1 during it. PAUSED music does NOT block it.
3. **Speech is sparse (low RMS)** so even when it plays it's ~3x quieter than the continuous beep/music.
FIXES (all in voice_client.py):
- **Keepalive**: `_start_keepalive()` — a continuous INAUDIBLE stream (±3 int16 noise via `pw-play --raw -`, self-throttling thread) to X10 so the sink NEVER idles. Essential.
- **Pause, don't duck**: on wake `pause_music()` (soloist+sc pause) for the whole interaction, `resume_music()` in finally (guarded by `if music` and a `resume` flag that honors an explicit pause/stop). Skip: `next` AUTO-PLAYS the new track, so re-`pause` right after, announce, return → finally resumes → new song from ~0:00. This also nails Matthew's spec (music off during voice, song from top after).
- **Compression**: tanh soft-knee in `_say` raises speech RMS to ~beep level. `SPEECH_COMPRESS` env (6≈beep loud; set to 4 = comfortable). One-number volume dial for the VOICE.
- **Don't churn the sink volume** (`wpctl @DEFAULT_AUDIO_SINK@`): BT AVRCP absolute-volume couples it to the speaker hardware and DRIFTS it down over repeated changes. Control music via soloist stream vol; leave the sink alone. (Permanent fix TODO: disable BT hw-volume in WirePlumber.)
Debug tool that cracked it: record the sink monitor and measure rms in 0.5s windows to see what ACTUALLY reaches the speaker vs what pw-play claims (rc=0 lies).
