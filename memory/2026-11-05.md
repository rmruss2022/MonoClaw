## [mac] 🔧 GOTCHA: `openclaw config set` value mode does NOT parse JSON

Setting a `string[]` field the obvious way fails with a bare **"config invalid"**:
```
openclaw config set commands.ownerAllowFrom '["telegram:5574760589"]'       # ✗ stores a STRING
openclaw config set commands.ownerAllowFrom '["telegram:5574760589"]' --strict-json   # ✓ stores an ARRAY
```
Plain value mode stores the argument as a literal string, so a `string[]` field got `"[\"telegram:...\"]"`. The CLI only discloses this in a dry-run note: *"value mode does not run schema/resolvability checks."* **A passing value-mode `--dry-run` therefore proves nothing.** Always `--strict-json` for arrays/objects/numbers/booleans, and verify the stored **type**, not the value: `jq '{v:.commands.ownerAllowFrom, t:(.commands.ownerAllowFrom|type)}'`. `openclaw config validate` is read-only and the fastest check; `openclaw doctor` will NOT catch it (the bad write never persists). Both can take 1-2 min — slow, not hung.

`commands.ownerAllowFrom = ["telegram:5574760589"]` now set on the Mac, so owner-only commands (`/restart`, `/update`) work from Telegram. Note it **hot-reloaded** (11:06 write → 11:09 applied) — no restart needed for that path.

## [mac] creator-cut: per-cut transitions SHIPPED (claimed; commit `8469fc0` on creator-cut/main)

Matthew's ask: transitions editable per cut like beat slices, and **the time must come out of the tail of the preceding clip and the head of the next** so nothing drifts off the beat. Length and type both editable.

**Repo note:** `creator-cut` is its own GitHub repo (`rmruss2022/creator-cut`), NOT in MonoClaw. Cloned to `~/creator-cut` on the Mac. TS monorepo: `shared/` + `server/` (Express) + `web/` (React/Vite). No test framework — tests are `check:*` scripts run with `tsx`, aggregated in `server` `npm run check`. House style is long reasoning-prose doc comments; match it.

**What was already there:** `ProjectSettings.transition` + `transitionMs` — *global*, one setting for the whole edit. `dissolveTogether()` in `render.ts` already solved beat-drift by giving each clip a T-second tail it doesn't own. But it spends the whole transition **after** the cut, so A plays its full span and B's first T seconds fade up — the cut you hear and the cut you see drift apart by T. Left intact as the fallback where no per-cut transition claims a join.

**The design.** Centring the blend on the cut is what makes Matthew's requirement exact: half out of the end of A, half out of the start of B, so the blend's midpoint *is* the beat. Every clip keeps its grid span, the total is unchanged, and **nothing needs trimming at the end** (the old path ran one transition long and trimmed).
- Offset for each join = `cut − durationSec/2`, measured from the run start. The accumulated stream always ends exactly where the blend closes, so xfade eats reach instead of timeline.
- Cost is **footage on both sides** — A must roll past its out point, B must reach back before its in point. Either can run out, so `maxTransitionAt()` / `transitionRefusal()` / `clampTransition()` are pure functions both UI and server call (the folder's existing rule: never offer what the server will refuse). Length is **clamped, not rejected**.
- Stored as `TimelineClip.transitionIn` on the clip to the **right** of the cut — the only placement that survives reorder, and the first clip correctly can't have one.
- `blendRuns()` keeps plain cuts on the cheap stream-copy concat path: 3 dissolves in a 200-clip edit re-encode 6 clips, not 200.

**Two traps worth remembering:**
1. `clipFilter()` used absolute timestamps (`st=0`, `st=duration−FADE_SEC`) and a frame count from `durationSec`. A clip with head reach starts `headSec` into its own part file, so **every fade fired early and the zoom finished early and froze**. Now works in encoded-file time. Also suppresses the global dip/flash on any join a per-cut transition already blends, or it darkens twice.
2. `flatten.ts` `pushPiece()` enumerates fields explicitly, so `transitionIn` was dropped. Carried through — but **only onto the piece that opens a clip**. A clip split around an overlay has a far half whose boundary is not a cut; giving it the transition would blend a shot into itself.

**Verification:** `check:transitions` — 42 assertions incl. "adding transitions moves no clip and changes no total". `check:transitions:real` — builds it with **real ffmpeg** on synthetic sources, two kinds at two lengths (dissolve 0.4s, wipe-left 0.6s): **3.000s in, 3.000s out**, offsets 0.800 and 1.700 exactly as centring predicts. All 9 xfade names verified to exist in the local ffmpeg. Full `typecheck` clean, web builds, and `cuts`/`layers`/`undo`/`reorder`/`grid` all still pass. `check:transitions` added to the aggregate `check` chain.

UI: per-cut kind dropdown + length slider in `CutsSheet`, slider max = `maxTransitionAt` so it stops where the footage stops; commits on pointer/key release (one undo step per drag). A join that can't pay shows a disabled "cut" with the reason in its title.

**Not done:** no visual marker for a transition on the `Timeline`/`CutView` strip yet, and the monitor's preview doesn't show blends (it cuts hard). Kinds are rendered but not previewed. Nine kinds offered: dissolve, dip, flash, wipe l/r/up, slide l/r, blur.

## [mac] creator-cut: transition strip marker + GPU preview (commit `091c3be`)

Closed the two gaps left by `8469fc0`.

**Strip:** a transition is drawn as the span it occupies — centred on its cut, width = blend length — so half visibly reaches into each neighbour. That *is* the model made visible. Click opens the cut panel, which now carries kind + length (`.cutview-trans`). The cut mark keeps its position and only gains a `.blended` class, because the cut hasn't moved.

**Preview — the research, and why we did NOT follow it literally.** Industry standard is GPU compositing of two decoded frames: BBC **VideoContext** (WebGL `TransitionNode` shaders), **cutaway** (PixiJS compositor), **5AM Video Studio** (WebCodecs + Web Workers + OffscreenCanvas), IMG.LY CE.SDK, `transition-studio` (WebGL in a worker). They all need shaders because they're *general* compositors.

This monitor isn't. All nine kinds reduce to opacity ramp / `clip-path` inset / `translate` / `blur` — every one a property the browser already composites on the GPU, **zero per-frame JS, zero texture upload**. A canvas would mean 2 `texImage2D` per frame handing the GPU pixels it already holds: strictly more work, same picture, plus a full monitor rewrite. So: two stacked `<video>` elements + composited props driven off blend progress. Logic in `web/src/blend.ts`; `will-change` + `backface-visibility` in CSS promote both surfaces to their own layers.

**The real blocker (worth remembering):** monitor `<video>` elements were keyed by **source**, and this app cuts one long source into many clips — so a dissolve between two clips *of the same file* could only ever show one of the two frames. One element cannot be parked at two instants. `partnerSources()` finds exactly the files appearing on both sides of some blend; the monitor allocates a second surface only for those (`surfaceKey(videoId, partner)`), instead of doubling every element.

**Shared so preview and render can't diverge:** `blendAt(clips, sec)` → `{fromIndex, toIndex, transition, atSec, progress}` with `progress` the same 0..1 xfade gets. `sourceTimeFor(clip, sec)` = the renderer's reach expressed as a seek (outgoing past its out point, incoming before its in point). Both sides are kept *playing*, not just seeked, or the incoming clip shows a still.

Dip/flash swap at the midpoint under a rising/falling veil (`.program-veil`, z-index between video and text) — a crossfade with a flash in the middle is not a dip.

**Verified:** `check:transitions` now 66 assertions (added: window opens half-early/closes half-late, progress 0.5 exactly at the cut and monotonic across the window, two blends never confused, partner allocated exactly when one file is on both sides). `check:transitions:real` still 3.000s in / 3.000s out. Full typecheck clean, web builds, `cuts`/`layers`/`undo`/`reorder`/`grid`/`window`/`musical` all pass.

**Still open:** never run in a browser by me — logic and build are verified, the actual on-screen blend is unproven. Worth Matthew eyeballing via `npm run dev`. Also: the hand-set clip framing and a slide's translate are composed into one `transform` string; if both are extreme that composition may need revisiting.
